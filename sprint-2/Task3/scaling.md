# Масштабирование баз данных

## Стратегия масштабирования

| Сервис | Стратегия масштабирования | Обоснование |
|---|---|---|
| Сервис ставок | Горизонтальное масштабирование runtime + Redis Cluster | В hot path нужны быстрые чтения. Данные кампаний читаются из кэша/read-модели, а не напрямую из PostgreSQL. |
| Сервис кампаний | PostgreSQL primary + read replica | Записи выполняются в primary, чтение для dashboard и служебных сценариев можно отправлять на replica. |
| Сервис статистики | Kafka partitioning + batch consumers + шардирование по времени/кампании | Поток кликов и показов большой и append-only. Партиционирование позволяет параллельно обрабатывать события. |
| Сервис аналитики | ClickHouse cluster + партиционирование по дате | Аналитика работает с большими объёмами исторических данных и агрегирующими запросами. |
| Сервис финансов | PostgreSQL primary + standby replica | Финансовые операции требуют строгой консистентности. Шардирование на первом этапе нецелесообразно. |

---

## Репликация Master-Slave / Primary-Replica

Репликация нужна там, где есть read-heavy нагрузка или требования к отказоустойчивости.

Применение:
- `Campaign DB` — primary для записи, read replica для чтения из dashboard и служебных запросов;
- `Billing DB` — primary + standby replica для failover;
- `Analytics DB` — кластер/реплики для распределения аналитических запросов;
- `Statistics DB` — реплики возможны для чтения агрегатов и отчётов.

Для RTB hot path прямое чтение из PostgreSQL должно быть минимизировано за счёт Redis/read-модели.

## Шардирование

| Данные | Ключ шардирования | Причина |
|---|---|---|
| События показов и кликов | `event_date` + `campaign_id` | Удобно хранить большой append-only поток и удалять старые партиции |
| Auction events | `event_date` + `auction_id` | Равномерное распределение и быстрый поиск по событию |
| Аналитические факты | `event_date` + `advertiser_id` / `campaign_id` | Основные отчёты строятся по периоду, рекламодателю и кампании |
| Кампании | Обычно без шардирования на первом этапе | Объём меньше, важнее консистентность и простота |
| Финансовые операции | Обычно без шардирования на первом этапе | Нужны строгие транзакции и аудит |

## Read replicas для аналитики

Аналитические запросы не должны выполняться на production OLTP-базах.

Для аналитики используется отдельное OLAP-хранилище, например ClickHouse.

Поток данных:

```text
Kafka
  -> Statistics consumers
  -> ClickHouse / Analytics DB
  -> Analytics Service
```

Read replicas PostgreSQL можно использовать как промежуточное решение, но для долгосрочной цели лучше вынести аналитику в отдельное OLAP-хранилище.

## CQRS

CQRS применим там, где read и write модели имеют разный профиль нагрузки.

| Область | Решение |
|----|----|
| Campaign Service | Запись кампаний в PostgreSQL, чтение активных кампаний через Redis/read-модель |
| Bidding Service | Использует только read-модель для быстрого принятия решения |
| Analytics Service | Читает из отдельной аналитической модели, построенной из событий |
| Statistics Service | Пишет raw events и агрегаты отдельно от RTB-потока |
| Billing Service | CQRS ограниченно: write-модель остаётся транзакционной, read-модель может использоваться для dashboard |
