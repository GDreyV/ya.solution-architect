# Database per Service

## Стратегия данных

| Сервис | Тип базы данных | Обоснование |
|----|----|----|
| Сервис ставок | Redis / in-memory cache + Kafka events | Сервис находится в latency-critical path и должен быстро читать активные кампании, ставки и targeting rules. Master-data не хранит, использует read-модель из кэша. Результаты аукционов публикует как события. |
| Сервис кампаний | PostgreSQL | Хранит master-data кампаний: настройки, ставки, таргетинг, статусы, креативы. Нужны транзакции, целостность данных и удобные CRUD-операции. |
| Сервис статистики | Kafka + PostgreSQL/ClickHouse для агрегатов | Принимает большой поток событий показов и кликов. Kafka используется как буфер и event log, запись в хранилище выполняется батчами. |
| Сервис аналитики | ClickHouse / OLAP-хранилище | Аналитика требует быстрых агрегирующих запросов по большим объёмам событий. OLAP-хранилище отделяет тяжёлые отчёты от transactional DB. |
| Сервис финансов | PostgreSQL | Финансовые операции требуют строгой консистентности, транзакций, аудита и идемпотентности списаний. |

## Принцип

Каждый сервис владеет своей моделью данных и не обращается напрямую к базе данных другого сервиса. Обмен данными выполняется через API или события.

Для RTB-потока приоритет — минимальная latency, поэтому сервис ставок использует кэшированную read-модель, а не прямые запросы к PostgreSQL.
