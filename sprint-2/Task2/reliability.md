# Паттерны надёжности

## 1. Цель

RTB-сервис должен сохранять предсказуемое время ответа даже при деградации зависимых компонентов. Для RTB лучше быстро вернуть `no-bid`, чем ждать ответ зависимого сервиса и нарушить SLA.

## 2. Circuit Breaker

Circuit Breaker используется для вызовов зависимых сервисов:
- Campaign Service;
- Billing Service;
- внешние DSP/API;
- Redis/cache;
- event broker.

Если сервис начинает отвечать медленно или с ошибками, circuit breaker временно прекращает вызовы к нему.

Поведение:
- `closed` — сервис работает штатно;
- `open` — вызовы временно блокируются;
- `half-open` — выполняются пробные запросы для проверки восстановления.

Для RTB timeout должен быть коротким: если зависимость не отвечает быстро, запрос обрабатывается через fallback.


## 3. Retries с экспоненциальной задержкой

Повторные попытки используются только для операций, где это безопасно:
- публикация событий в Kafka;
- служебные запросы;
- обновление кэша;
- фоновые операции.

Для latency-critical bid request retries не должны увеличивать время ответа.

Пример политики:

```text
retry count: 2-3
backoff: 50ms -> 100ms -> 200ms
jitter: enabled
```

Для внешнего RTB-запроса лучше вернуть 204 No Content, чем делать долгие повторные попытки.

## 4. Идемпотентность финансовых операций

Финансовые операции должны быть идемпотентными, так как события могут быть доставлены повторно.

Для этого используется:
- уникальный transaction_id;
- уникальный auction_id / impression_id;
- таблица обработанных операций;
- проверка перед списанием средств;
- атомарная транзакция списания и записи результата.

Пример:
```text
if transaction_id already processed:
    return previous result
else:
    charge budget and save transaction
```

Это защищает от повторного списания бюджета при retries или повторной доставке событий.

## 5. Резервные стратегии

Если зависимость недоступна, Bidding Service использует fallback.

Возможные fallback-стратегии:

| Сценарий | Поведение |
|----|----|
| Campaign Service недоступен | Использовать последнюю валидную версию кампаний из кэша |
| Redis недоступен | Использовать локальный in-memory cache с коротким TTL |
| Нет валидных данных кампаний | Вернуть 204 No Content |
| Billing Service недоступен | Использовать BudgetSnapshot, событие списания отправить асинхронно |
| Kafka недоступна | Локальный outbox / retry buffer, затем повторная публикация |
| Рост latency Bidding Service | Gateway возвращает no-bid или ограничивает трафик |

## 6. Кэшированные и дефолтные ставки

Для снижения зависимости от Campaign Service используются:
- кэш активных кампаний;
- кэш targeting rules;
- кэш bid rules;
- BudgetSnapshot.

Если свежие данные недоступны, сервис может использовать последнюю валидную версию данных с ограниченным TTL.

Дефолтные ставки допустимы только для заранее разрешённых кампаний и не должны нарушать бюджетные ограничения.

## 7. Observability

Для контроля надёжности собираются метрики:
- circuit breaker state;
- retry count;
- fallback rate;
- timeout rate;
- Kafka publish errors;
- cache hit ratio;
- no-bid rate;
- P95/P99 latency.

По критичным метрикам настраиваются алерты.
