# Протоколы и паттерны взаимодействия

## 1. Внешняя интеграция с DSP

Для интеграции с DSP используется `HTTPS / OpenRTB`.

DSP отправляет `bid request`, AdScale возвращает `bid response` или `204 No Content`, если подходящей рекламы нет.

Причины выбора:
- OpenRTB является стандартным протоколом RTB-интеграций;
- HTTP хорошо поддерживается DSP-платформами;
- проще обеспечить rate limiting, timeout и observability на edge-уровне.

---

## 2. API Gateway

В качестве API Gateway выбран `NGINX + Lua`.

Gateway отвечает за:
- TLS termination;
- routing;
- rate limiting;
- request validation;
- timeout policy;
- базовую защиту от перегрузки;
- логирование технических метрик.

Причины выбора:
- высокая производительность;
- простота внедрения;
- open-source;
- низкая стоимость;
- достаточно гибкая настройка через Lua.

---

## 3. Внутренние синхронные взаимодействия

Для взаимодействия `Bidding Service` и `Campaign Service` используется `gRPC`.

Причины выбора:
- низкая overhead по сравнению с REST;
- строгий контракт через `.proto`;
- удобная генерация клиентов;
- лучше подходит для latency-sensitive внутренних вызовов;
- хорошо работает при high-RPS нагрузке.

При этом Bidding Service должен в основном читать данные кампаний из кэша. gRPC-вызов к Campaign Service используется для cache miss, обновления read-модели или служебных сценариев.

Для UI/backend взаимодействий используется `REST`, так как dashboard выполняет CRUD-операции и не находится в latency-critical path.

---

## 4. Асинхронные события

Для событий показов, кликов и результатов аукционов используется `Kafka`.

Поток событий:

```text
Bidding Service
  → Kafka
  → Statistics Service
  → Analytics Storage
  → Billing / Anti-fraud consumers
```

Причины выбора Kafka:
- подходит для большого потока append-only событий;
- поддерживает consumer groups;
- позволяет нескольким сервисам независимо читать одни и те же события;
- хранит события некоторое время и позволяет replay;
- отделяет RTB hot path от статистики и аналитики.

## 5. Общий принцип

Синхронные вызовы используются только там, где результат нужен для ответа пользователю или DSP.

Асинхронные события используются там, где допустима eventual consistency:
- показы;
- клики;
- auction events;
- агрегирование статистики;
- аналитика;
- биллинговые события.
