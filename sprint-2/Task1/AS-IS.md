# AS-IS

## Обзор

Текущая архитектура AdScale представляет из себя гибридный монолит, состоящих из различных технологий (C++, Go, Python, Node.js), и работающий на единственном инстансе PostgreSQL.

Одно приложение и база данных обслуживают аукционы в реальном времени (Real-Time Bidding, или RTB), управление кампаниями, аналитику, финансовую отчетность и аггрегацию событий.

С текущем профилем нагрузки AdScale уже работает почти на пределе своих возможностей:
- пиковый траффик 15 000 RPS
- P95 времени отклика 110–120 ms
- Периодические деградации в часы пик
- Отсутствие запаса по производительности

Планируемая интеграция с крупной DSP-площадкой (Demand-Side Platform) увеличит траффик примерно на 20% сразу, а через год ожидается более чем двукратный рост до 50 000 RPS. Текущая архитектура не предусматривает такой нагрузки без существенных изменений.

# Критические узлы

Наиболее критическим к деградации маршрутом вызовов компонентов является система ставок реального времени (Real-Time Bidding, RTB):

```text
DSP Partner
    -> Ad Server
    -> Auction Engine
    -> Delivery Service
    -> Bid Response
```

Этот путь отвечает за обработку ставок в реальном времени и должен удовлетворять строгим требованиям SLA.

Архитектура построена преимущественно на синхронных взаимодействиях и прямых JDBC-вызовах к общей базе данных. Асинхронная обработка, очереди сообщений, кэширование и разделение workloads отсутствуют.

# Архитектурные проблемы

## Общая база данных

Единая PostgreSQL-база данных как Single Point of Failure

В системе используется одна PostgreSQL-инстанция для:
- RTB-аукционов;
- хранения кампаний;
- статистики;
- финансовых операций;
- аналитики;
- dashboard workload.

Проблемы текущего подхода:
- отсутствие High Availability;
- отсутствие read replicas;
- отсутствие workload isolation;
- конкуренция OLTP и аналитических запросов;
- невозможность независимого масштабирования.

Любая деградация или недоступность PostgreSQL приводит к отказу всей платформы.

## Отсутствие кэша

## Отсутствие кэширования

Ad Server и Auction Engine читают из PostgreSQL данные о кампаниях, ставках, таргетинге и правилах аукциона. Эти данные, вероятно, не изменяются несколько раз в секунду, поэтому часть read-нагрузки можно было бы обслуживать из кэша.

Отсутствие кэширования увеличивает количество обращений к PostgreSQL в RTB-потоке и делает latency аукциона более зависимой от состояния общей БД. Кэширование активных кампаний, ставок и targeting data могло бы снизить нагрузку на БД и уменьшить задержки в критическом пути.

## Монолит

## Ограничения монолитной архитектуры

Монолитная архитектура усложняет точечное масштабирование системы. Даже если основная нагрузка приходится на Ad Server, Auction Engine или Statistics Service, масштабировать приходится весь монолит целиком, вместе с менее нагруженными компонентами.

Это делает масштабирование более дорогим и менее эффективным: увеличивается потребление CPU и памяти, растёт количество экземпляров приложения и количество подключений к общей PostgreSQL-базе данных.

При росте числа инстансов монолита также возрастает нагрузка на connection pool PostgreSQL. Для контроля количества соединений может потребоваться отдельный DB proxy или connection pooler, например PgBouncer. Однако это решает только проблему управления соединениями, но не устраняет архитектурную связанность компонентов и конкуренцию за ресурсы общей БД.
