# Выбор архитектурного стиля

Миграция сразу на микросервисную архитектуру не подходит из-за ограниченных сроков (3 месяца), ограниченного бюджета и высокого риска для работающей RTB-платформы.

Сохранение текущего монолита также не решает существующие проблемы:
* shared PostgreSQL bottleneck;
* отсутствие workload isolation;
* невозможность независимо масштабировать наиболее нагруженные компоненты;
* деградация latency RTB-аукционов при росте нагрузки.

Оптимальным подходом является постепенная декомпозиция системы с использованием Strangler Fig Pattern.

На промежуточном этапе наиболее критичные по нагрузке и масштабированию части системы постепенно выделяются из монолита:

* event ingestion / statistics pipeline;
* analytics workload;
* bidding infrastructure.

При этом latency-critical RTB-поток (Ad Server, Auction Engine, Delivery Service) целесообразно сохранить в рамках единого RTB Runtime / модульного монолита. Для этого потока важнее минимальная latency и отсутствие лишних network hops, чем формальное разделение на отдельные микросервисы.

Декомпозицию следует применять избирательно: в первую очередь выносить компоненты с другим профилем нагрузки и требованиями к консистентности — statistics/event ingestion, analytics и финансовые операции.

Такой подход:

* снижает риск миграции;
* позволяет сохранить непрерывность бизнеса;
* даёт возможность постепенно внедрять новую инфраструктуру;
* позволяет масштабировать наиболее нагруженные компоненты независимо;
* создаёт основу для перехода к микросервисной event-driven архитектуре в будущем.
