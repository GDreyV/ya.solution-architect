# 4.3. Базовые меры безопасности

## Аутентификация мобильного приложения

Используется стандартный механизм OIDC — Authorization Code с PKCE для публичного мобильного клиента. Client secret в приложение не помещается. После входа приложение получает короткоживущий access token в формате JWT и refresh token. Access token передаётся только по HTTPS в заголовке `Authorization: Bearer <token>`, а refresh token хранится в защищённом хранилище ОС и ротируется. `patientId` для внутренних запросов берётся из проверенного токена, а не из параметров клиента.

## Политика Rate Limiting

| Тип запроса | Лимит | Действие при превышении |
|---|---|---|
| Публичный `GET /api/v1/doctors/search` | 60 запросов в минуту на IP, burst 10 | `429 Too Many Requests`, `Retry-After`; событие в метрики, временная блокировка явно аномальных IP |
| Авторизованный `POST /api/v1/appointments` | 5 запросов в минуту на пользователя, burst 2 | `429` и `Retry-After`; уже принятую команду можно безопасно повторить с тем же `Idempotency-Key` |

Лимиты — начальная политика MVP; после нагрузочного тестирования и анализа реального поведения они корректируются. Лимит поиска выше, потому что это чтение; создание записи ниже из-за изменения состояния и риска занять несколько слотов.

## Защита данных при передаче

- TLS между приложением и API Gateway; запрет HTTP, проверка сертификата, HSTS для веб-интерфейса.
- TLS, а для внутренних HTTP API — mTLS, между API Gateway, сервисом API мобильного приложения и внутренними системами; отдельные сервисные учётные данные с минимальными правами.
- AMQPS для RabbitMQ, отдельные пользователи и права на конкретные exchange/queue; persistent messages не заменяют шифрование канала.
- Не передавать токены, медицинские данные и полные тела запросов в URL и технические логи; маскировать идентификаторы и заголовок Authorization.
- Авторизация на каждый объект: пациент получает только свои записи и анализы; `patientId` берётся из токена, а не из параметра клиента.
- Валидация входных данных и параметризованные SQL-запросы, чтобы закрыть зафиксированную SQL-инъекцию.
- Короткий срок access token, ротация и отзыв refresh token, защита от повторного использования сессии.
