# Задание 3. Целевая облачная архитектура VitaStore

## Аудит AS-IS

Исходная схема в целом верно показывает толстый POS-клиент, локальную БД и прямую связь кассы с фискальным регистратором и терминалом. Ошибка схемы — `Real-time REST API` между POS и SAP ERP. Согласно действующему регламенту, товарные данные после ручного сопоставления в Excel загружаются в SAP, а SAP в 02:00 формирует XML и рассылает его по FTP на локальные серверы магазинов. Поэтому в исправленной AS-IS-схеме показаны пакетный обмен и ручной контур `CSV/XLS -> email -> Excel/VLOOKUP -> SAP`.

Текущая архитектура имеет две критические точки связанности. POS содержит драйверы конкретных моделей устройств, поэтому подключение ARCUS-2 или другого протокола требует разработки и пересборки монолита. Local DB является одновременно хранилищем и точкой отказа: поломка диска останавливает магазин и требует выезда инженера.

## Переход к Cloud-Native

Целевая схема переносит master-данные и кассовую бизнес-логику в Cloud POS Backend с управляемой БД. В магазине остаются планшет, заменяемый Store Edge Runtime и оборудование. Edge не является прежним локальным сервером: он не хранит master-БД, не требует Windows Server/MS SQL и может быть автоматически восстановлен из облачной конфигурации. Его назначение ограничено доступом к локальному оборудованию и минимальным автономным контуром продажи.

HAL (Hardware Abstraction Layer) предоставляет POS стабильный локальный API и скрывает различия COM, USB и vendor-протоколов. Драйверы оформляются как подписанные версионируемые адаптеры; выбор адаптера задаётся конфигурацией магазина. Облачный Payment Gateway унифицирует взаимодействие с банками и эквайерами, а локальный HAL отвечает за физический терминал. Поэтому подключение новой модели требует добавить и сертифицировать адаптер, не меняя кассовое приложение.

Рекомендуемый переход: сначала развернуть Cloud Backend и синхронизацию параллельно текущей системе; затем вынести драйверы в HAL и подключить толстый POS через единый API; после пилота заменить клиент на планшетный Thin POS; в конце мигрировать чеки, отключить Local DB и вывести серверы из эксплуатации. Функциональные флаги и поэтапное подключение магазинов позволяют откатить отдельную точку без остановки всей сети.

## Offline-mode и синхронизация

Edge заранее получает версионированный snapshot товаров, цен, налоговых ставок и тех промо-правил, которые разрешено исполнять локально. При обрыве связи Thin POS переключается на локальный Edge API. Наличная продажа проводится в локальной транзакции: операция получает глобально уникальный `operationId`, фискализируется через HAL, а событие и статус чека атомарно записываются в append-only журнал и transactional outbox. Облачные функции, для которых нельзя гарантировать актуальность или авторизацию, например списание бонусов, блокируются; банковская оплата доступна только если терминал и эквайер поддерживают автономный режим по отдельным риск-правилам.

После восстановления интернета Sync Agent отправляет outbox пакетами в порядке локальной последовательности. Store Sync Service принимает команды идемпотентно по `operationId`, сохраняет checkpoint и повторная отправка не создаёт дубль продажи или чека. Конфликты решаются по владельцу данных: завершённая фискальная продажа с edge неизменяема и принимается как факт, а товары и цены принадлежат облаку и возвращаются на edge как новая версия snapshot/delta. Ошибочные или неразрешимые события попадают в quarantine/DLQ для ручной сверки, не блокируя остальные операции.

Сервер подтверждает пакет только после фиксации данных; до подтверждения события остаются в outbox. Затем edge получает входящие дельты через inbox, проверяет контрольную сумму и атомарно переключает активную версию кэша. Метрики отставания, размер очереди, последняя успешная синхронизация и версия адаптеров поступают в Monitoring & Device Management.
