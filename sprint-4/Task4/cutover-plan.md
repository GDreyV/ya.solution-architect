# Cutover plan пилотного логистического партнёра

## 1. Цель переключения

Перевести новые заказы одного логистического партнёра со старого интеграционного пути на Integration ACL без остановки оформления заказов.

Java-монолит и Oracle остаются основной системой. Меняется только способ отправки новых запросов выбранному партнёру.

## 2. Условия запуска

- новый адаптер прошёл функциональные и интеграционные тесты;
- партнёр подтвердил тестовые запросы и ответы;
- результаты нового и старого преобразования данных проверены в фоновом режиме;
- настроены логи и основные метрики;
- данные заказа в Oracle и read-модели совпадают;
- старый путь работает и готов принять весь трафик при откате;
- команда согласовала допустимый уровень ошибок;
- назначены ответственные за переключение и откат.

## 3. Роли и ответственность

| Роль | Ответственность |
|---|---|
| Руководитель миграции | Решение о начале, продолжении или откате |
| Команда интеграций | Переключение маршрута и исправление адаптера |
| Команда RetailCore | Контроль монолита и Oracle |
| Команда эксплуатации | Контроль метрик, логов и ошибок |
| Команда заказов | Проверка статусов и данных заказа |
| Представитель партнёра | Подтверждение получения запросов |
| Поддержка | Контроль обращений по пилотным заказам |

## 4. Пошаговый сценарий

### До переключения

1. Проверить доступность монолита, Oracle, брокера, старой интеграции и Integration ACL.
2. Убедиться, что необъяснённых ошибок в очередях нет.
3. Зафиксировать текущие показатели старого пути.
4. Проверить feature flag, управляющий маршрутом.
5. Уведомить участников и партнёра.

### Тестовое переключение

1. Направить через Integration ACL несколько внутренних тестовых заказов.
2. Для каждого заказа проверить: запись в Oracle, выбор нового маршрута, получение партнёром, обработку ответа и статус в read-модели.
3. Если есть ошибки, вернуть старый маршрут и устранить проблему.

### Постепенное переключение

1. Перевести на новый путь небольшую часть новых заказов партнёра.
2. Сравнить старый и новый пути по успешности, ошибкам и времени ответа.
3. Проверить отсутствие потерянных и повторных заказов.
4. Если результат приемлем, увеличить долю до 50%.
5. После повторной проверки перевести 100% новых заказов.
6. Старый путь оставить доступным на период наблюдения.

Заказ, уже отправленный через один из контуров, завершается в том же контуре. Это предотвращает повторную отправку партнёру.

## 5. Проверки после переключения

| Что проверяем | Ожидаемый результат |
|---|---|
| Оформление заказов | Ошибки и время ответа не ухудшились сверх допустимого уровня |
| Отправка партнёру | Каждый заказ отправлен один раз |
| Ответы партнёра | Ответы получены и обработаны |
| Состояние данных | Oracle, журнал интеграции и read-модель согласованы |
| Очереди | Нет растущей очереди необработанных сообщений |
| Наблюдаемость | По ID заказа можно найти связанные записи и ошибки |
| Поддержка | Нет новых критичных обращений |

## 6. Условия отката

Откат выполняется, если выросло число ошибок или время ответа, обнаружены потерянные или повторные заказы, ответы партнёра не обновляют заказ либо данные контуров существенно расходятся.

## 7. Rollback-сценарий

1. Остановить увеличение доли нового пути.
2. С помощью feature flag направить все новые заказы обратно в старый контур.
3. Проверить, что новые заказы действительно идут старым путём.
4. Составить список заказов, уже отправленных через Integration ACL.
5. Не отправлять их повторно: запросить состояние у партнёра и завершить обработку через новый контур.
6. Сверить Oracle, журнал интеграции и данные партнёра; разобрать зависшие операции.
7. Убедиться, что старый путь работает в обычном режиме.
8. Сообщить участникам и поддержке о завершении отката.

Повторное переключение проводится после исправления причины и повторного тестирования.

## 8. Критерии завершения

- все новые заказы выбранного партнёра проходят через Integration ACL;
- показатели остаются в допустимых пределах в течение периода наблюдения;
- нет потерянных и повторных заказов;
- данные Oracle, журнала интеграции и read-модели согласованы;
- команда может находить и разбирать ошибки нового пути;
- старый путь можно отключить отдельным изменением.
